### 1.2 MVP 的真实边界（必须如实说）

1. **是对内副驾，不是对外客服。** 使用者是客服员工，输出是"可复制的话术 + 依据 + 升级提示"，不直接对买家讲话。
2. **规则是按这 200 条调出来的。** 84.5% 是"这套题上的上限估计"，真实泛化要靠 blind set 或线上抽样校准。
3. **单轮评测。** 真实客服是多轮；"先追问"类失败在多轮里可能自然消失，也可能放大。
4. **工具数据是 mock。** 库存/物流是本地 JSON，接真实 ERP/WMS 之前，工具调用只能算"链路通了"。
5. **没有 judge。** 忠实度、语气、有用性没有 LLM 评分，只有规则断言 + 人工抽检。
6. **没有鉴权、没有日志留存、没有限流。** 这是网页端上线前必须补的三件事。
7. **密钥治理有历史债。** 旧 Dify Key 曾泄露到公开仓库并仍未吊销，上线前必须换新并只放服务端。

### 1.3 MVP 一句话判定

> 作为"内部客服副驾"的**可行性验证**，MVP 成立：链路真实、指标可复现、失败可归因；
> 作为"能上线给员工用的产品"，还差**一层网关 + 一个前端 + 一套线上观测**。

## 2. 上线目标与范围（小范围试点）

- **对象**：单个客服小组，5–10 人，2 周试点。
- **形态**：网页端（PC 浏览器），员工登录后贴买家原话 → 看到建议回复 + 依据 + 是否建议转主管 → 一键复制 / 标记"有用/没用"。
- **不做**：不接平台 IM、不自动回复买家、不做多租户、不做移动端。
- **成功标准**（试点结束判定）：
  - 建议采纳率 ≥ 60%（复制或基本照用）；
  - 平均处理时长下降 ≥ 15%（对比试点前一周基线）；
  - 员工 NPS ≥ 0（愿意继续用）；
  - 线上抽样 100 条，人工判定通过率 ≥ 80%。

## 3. 目标架构

```
浏览器（React/Next.js）
   │  HTTPS + 登录态
   ▼
Web 网关（FastAPI，新增）
   ├─ 鉴权（账号/工号 + 会话 Cookie 或 JWT）
   ├─ 限流（每员工每分钟 N 次）
   ├─ 日志落库（提问、回答、依据、动作、耗时、反馈）
   ├─ 敏感信息脱敏（手机号/地址/订单号部分掩码）
   └─ 调用 Dify：POST /v1/chat-messages（streaming）
         │
         ▼
Dify（现有 Chatflow，27 节点）
   ├─ 知识库（MMM 库，hybrid + rerank）
   └─ MCP 工具（库存 8000 / 物流 8001）
```

关键点：

1. **Dify Key 只放网关环境变量**，前端永远拿不到；
2. 用 `conversation_id` 支持追问，但 MVP 可以每条独立（先简单）；
3. 网关把 Dify 的 JSON 输出**解析后**再给前端，前端不解析模型原文；
4. 所有请求落 Postgres（复用 Dify 的库或独立库），字段见 4.2。

## 4. 开发计划（4 周，按周可验收）

### 第 1 周：网关 + 鉴权 + 日志（后端）

- [ ] 新建 `web/` 目录：FastAPI + SQLModel + Postgres（可用 Dify 的 `docker-db_postgres-1` 新建库 `copilot`）
- [ ] 接口：`POST /api/ask`（入参 buyer_message/order_no/agent_level/scene_hint）、`POST /api/feedback`、`GET /api/health`
- [ ] 简单账号体系：工号 + 密码（bcrypt），或直接接公司 LDAP/飞书扫码（有就优先）
- [ ] 限流：每员工 20 次/分钟，超限返回 429
- [ ] 日志表 `conversations`：id、员工、提问、回答、evidence、next_action、escalate、latency_ms、dify_message_id、反馈
- [ ] 密钥：新 Dify Key 写入网关 `.env`，服务端 only；删除旧 Key
- 验收：curl 能拿到结构化回答；日志表有记录；无 Key 泄露到前端。

### 第 2 周：前端 + 反馈闭环

- [ ] Next.js 单页：输入框（买家原话/订单号/场景）、员工经验切换、结果卡片（回复/依据/动作/是否转主管）
- [ ] "复制话术"按钮 + "有用/没用"反馈 + "这条不对"备注
- [ ] 展示 latency 与"依据来源文档名"，让员工能判断可信度
- [ ] 错误态：超时、模型失败、知识库为空时的兜底文案
- 验收：3 名同事能用真实工单跑通 20 条，反馈能落库。

### 第 3 周：灰度上线 + 观测

- [ ] 部署：内网服务器 docker compose（gateway + web + 复用现有 Dify）
- [ ] 看板（Grafana 或简单 SQL 报表）：日活、采纳率、转主管率、P50/P95、失败 Top5
- [ ] 每日抽 20 条人工复核，记录"通过/不通过/原因"
- [ ] 建立回归集：每周把线上失败样本 10 条并入 `testset_copilot.json`（新版本号，不覆盖旧版）
- 验收：连续 5 个工作日有数据；看板可查。

### 第 4 周：试点复盘 + 决策

- [ ] 汇总 4 个指标（采纳率、时长、NPS、抽检通过率）
- [ ] 输出《试点复盘》：哪些场景真有用、哪些场景员工不信、哪些失败是知识库缺口
- [ ] 决策：扩到全组 / 只保留高频场景 / 回炉重做
- [ ] 若扩量：再评估是否接真实 ERP/WMS、是否要 rerank 之外的召回优化

## 5. 上线前必须补的 6 件事（按优先级）

| # | 事项 | 为什么 | 工作量 |
|---|------|--------|--------|
| 1 | 换新 Dify Key、旧 Key 吊销 | 旧 Key 泄露在公开 git 历史里 | 0.5 天 |
| 2 | 网关鉴权 + 限流 | 否则任何人拿到 URL 就能刷 | 1 天 |
| 3 | 日志与脱敏 | 客服对话含手机号/地址，必须可审计 | 1 天 |
| 4 | 失败兜底 | 模型超时/JSON 坏时不能白屏 | 0.5 天 |
| 5 | 真实工具数据 | mock 库存/物流会给出错误承诺 | 依赖业务方 |
| 6 | 免责与边界提示 | 页面写明"建议仅供参考，以平台规则为准" | 0.5 天 |

## 6. 风险清单

| 风险 | 影响 | 缓解 |
|------|------|------|
| 模型编造政策/价格 | 员工照抄导致客诉 | 强制 evidence + 页面展示依据 + 抽检 |
| 规则过拟合测试集 | 线上通过率低于 84.5% | blind set 校准、线上失败样本回流 |
| Dify 单点故障 | 全员不可用 | 网关降级为"只查知识库/只给模板" |
| 成本失控 | 每会话 token 费用 | 限流 + 缓存高频问题 + 监控单会话成本 |
| 数据合规 | 买家信息外泄 | 脱敏、最小化留存、访问审计 |
| 员工不信任 | 采纳率低 | 显示依据与置信动作、允许一键纠错 |
