# 客服副驾：问题归因与解决总表

> 按项目节点记录：看到的现象 → 真正的根因 → 怎么修的 → 拿什么证明修好了

## 一、结论先行

- 这份表把客服副驾当成一个独立项目，从“开始改 Dify、搭副驾”算起，按时间顺序拆成 23 个节点。每个节点只回答四件事：现象是什么、根因在哪一层、做了什么、怎么验证。
- 一句话结论：这个项目里大部分“效果不好”不是模型不行，而是链路没通——分类器提示词被污染导致检索节点从未执行、if-else 的 false 分支断链、向量库只读导致索引静默失败、工具结果没拼进提示词。真正靠提示词拿到的提升有限，而且容易过拟合。
- 另一条同样重要的教训是采样：v3.7 单次 74.0%、隔天复跑只有 68%，所以从 v3.8 起统一“每版两轮、报合并值”，单轮只用来定位问题。

> 背景（不算归因节点）：更早还有一版“替买家直接回消息”的自动客服。因为平台不开放第三方消息接口，那个方向走不通，于是转成“客服副驾”——不替买家回，把可复制的话术和依据放到客服面前，由人发送。那一版的评测口径与数据属于另一个项目，本表不引用；本表从改 Dify、建副驾开始。

## 二、归因分层（排查顺序）

| 层 | 典型症状 |
| --- | --- |
| 口径层 | 指标定义错了，数字再好看也不代表线上。例：AHT 从 focus 起算、把单次采样当结论。 |
| 链路层 | 节点有没有被执行、分支有没有接上、变量有没有渲染。这一层的问题最像“模型笨”。 |
| 数据层 | 知识库有没有真的进向量库、检索词是否被清洗、阈值是否把结果全过滤。 |
| 配置层 | 模型供应商、参数名、枚举值、超时。多为 400/403/超时，日志里能直接看到。 |
| 提示词层 | 口吻、动作边界、输出格式。改这里见效快，但也最容易对着测试集过拟合。 |

## 三、节点总表

| 编号 | 阶段 | 现象 | 根因（分层） | 解决动作 | 验证与结果 |
| --- | --- | --- | --- | --- | --- |
| N1 | 迁移 Dify | 导入改好的 DSL，Dify 直接报错 | 协议层：改版后把买家原话换成了 buyer_message，而 Dify 校验要求 LLM 的 user 消息必须包含 sys.query | 改成：买家原话仍走 sys.query，开始节点只留订单号、经验、场景三个元数据变量 | 导入通过，接口正常返回 |
| N2 | 首评 60 条 | 第一轮只有 41.7%，看着像模型不会答 | 数据层+解析层：4 份客服知识库还没上传（evidence 全空）；模型把 <think> 推理写进回答、回答被截断；断言把“按规则追问”判成错 | 先补知识库；剥掉 think；放宽存储；把 18 条断言改成多动作/不判升级 | 第二轮 61.7%，失败从“没依据”转为“动作不对” |

| N12 | 分类器提示词污染（最核心） | 知识库有内容，回答却说“不知道” | 链路层：路由分类器的提示词被历史补丁追加了回答节点的输出纪律，分类器输出客服 JSON 而不是场景词；if-else 判 false，知识检索节点从未执行 | intent.md 重写成纯路由（只输出一个场景词） | 探针 resources 从 0 变 2–3 条；200 条上单项约 +3.5 点 |

## 六、下次遇到“效果不好”的排查清单

1. 先看链路：分类器输出对不对？if-else 走的是哪条边？false 分支有没有接？检索节点到底有没有执行？
2. 再看数据：向量库里有多少对象、和文档分段数对不对得上？检索词有没有被清洗？阈值是多少？
3. 然后看配置：模型供应商、参数名、枚举值、超时。400/403 基本都在这一层。
4. 最后才调提示词：一次只改一类规则，改完跑两轮，两轮都涨才认。
5. 任何“提升”都要问三句：换一套题还成立吗？两轮都成立吗？是链路修好了还是话术背下来了？
